## 一、游戏概览

Chrome 离线小恐龙的复刻。跑动 -> 跳过障碍 -> 撞到就 Game Over -> 按键重开。

| 项 | 值 |
|---|---|
| 画布 | 1600 x 900 |
| 地面线 | `top = 700` |
| 循环步长 | 固定 `1/50` 秒（**不是**真实帧间隔） |
| 操作 | 空格 / ↑（`KeyboardJumpKeyDown/Up`） |

**★ 为什么用固定步长：** 真机 `TweenSequence` 的调度抖动有 5~12ms
（见 `引擎能力与限制.md` §4.6.3），用固定步长做物理**结果可复现**、
不受掉帧影响。

**★ 每个精灵用独立的格宽**（单位 px）：

| 精灵 | 点阵 | 格宽 | 尺寸 |
|---|---|---|---|
| 恐龙 | 22x24 | **5.67**（浮点） | 125 x 136 |
| 仙人掌 / 翼龙 / 云 | — | 8 | 见各节 |

> ⚠️ 恐龙用浮点格宽是为了「高度 = 中仙人掌 136px」且**不丢眼睛**
> （见 §2.1）。其他精灵一律 8px。

## 二、精灵点阵与摆放几何

### 2.1 为什么恐龙是 22x24 + 浮点格宽

**需求：** 恐龙高度 = 中仙人掌高度（136px）。

**第一版做法（已推翻）：** 把恐龙点阵从 22x24 重采样到 16x17 格（136px）。
结果**眼睛丢了** —— 眼睛只占 1 格，重采样时被采样吞掉。

**R26 正解：** 回到 22x24 原版点阵（含眼睛），把格宽缩小：

```
DINO_CELL = 136 / 24 = 5.67px
22 格 x 5.67 = 125px 宽
24 格 x 5.67 = 136px 高  ← 与中仙人掌等高
眼睛 = 5.67 - 2x1(bleed) = 3.67px 可见
```

**★ 重采样要点（若将来必须重采样）：**

- 用**覆盖率**而非中心点（中心点会漏掉细连接）
- 重采样后必须用**连通域**验证是单一整块
- **不要为等高而重采样小细节** —— 眼睛这种 1 格细节一定会丢

### 2.2 ★★ 摆放几何：脚必须踩在地面线上

**这是换了精灵尺寸后最容易错、且最难看出来的地方。**

```
地面线 .ground top = 700
恐龙点阵高 136，脚在控件顶 +136
-> 恐龙容器 top = 700 - 136 = 564          (= G.GROUND_Y)

地面障碍底边都对齐地面线：
-> 容器 top = 700 - 高度px
   大仙人掌(144) -> 556
   中仙人掌(136) -> 564
   小仙人掌( 96) -> 604
```

> ⚠️ 若沿用旧尺寸的 top，恐龙会**陷进地面**，
> 而画面上只是"位置有点怪"，**不报错**。

**回归：** `tests/test_demo_dino_run.lua` 断言
「恐龙脚 = 地面线 700」（误差 < 1px）。

### 2.3 精灵清单与矩形数

| 精灵 | 逻辑尺寸（格） | 矩形数 |
|---|---|---|
| 恐龙站立 | 22 x 24 | 31 |
| 恐龙跑动 | 22 x 24 | — |
| 恐龙死亡 | 22 x 24 | — |
| 翼龙（三帧） | 20 x 10 | 15 / 14 / 12 |
| 云 | 10 x 5 | 6 |
| 地面装饰 | 5x2 / 7x2 / 3x2 | — |

**★ 用贪心最大矩形分解，不是逐行分段：** 逐行分段会产生大量细长条
（恐龙要 70 段），贪心只要 31 个 —— **少一半控件**。

> 分解与渲染的**引擎侧约束**（`position:absolute` / bleed / image 控件 /
> 圆角）见 `引擎能力与限制.md` §4.7。

## 三、可解性：三条几何约束

> **这一整节是「游戏设计约束」，不是引擎能力。**
> 但它比引擎限制更危险：违反后**游戏看起来完全正常、不报错、不崩溃**，
> 只是变得**不可通关**。

### 3.1 尺寸基准：恐龙与中仙人掌等高

```
中仙人掌 17 格 x 8px = 136px = 恐龙高度
```

### 3.2 跳跃高度：峰值必须留足余量

```
峰值公式  H = v² / (2g)
v = 1600, g = 6100  ->  H = 209.8px
最高仙人掌（大）= 144px  ->  余量 66px ✓
```

**★ 判据不是「峰值数字 > 障碍高度」，而是「碰撞盒底 < 障碍顶」。**
后者才是真正决定能否越过的量：

```
峰值时恐龙盒底 = 466
大仙人掌顶     = 556      ->  余量 90px ✓
```

**★ v 与 g 必须【同时】提高：**

| 参数 | 峰值 | 全程 | 手感 |
|---|---|---|---|
| 旧 v=1150 g=4200 | 157px | 0.548s | 基准 |
| v=1330 g=4200 | 210px | **0.633s** | **慢了 15%（用户反馈）** |
| **v=1600 g=6100** | **210px** | **0.525s** | 更快 ✓ |

> **教训：只提初速不提重力，跳跃全程会变长（上升更久、落地更慢），
> 手感"拖沓"。**

### 3.3 ★★★ 约束一：翼龙高度必须在【跳跃可达范围】内

**恐龙碰撞盒：** 站立 `620..676`，跳到峰值 `410..466`
（`DINO_HIT_T=56` / `DINO_HIT_B=112`）

```
=> 恐龙 top 的可达区间 = [354, 564]
```

**★ 旧版只有 603 / 405 两档，405 那档被用户判定"高度不对"。**

原因是 405 的盒子(413..485)**几乎完全压在峰值盒(410..466)上** ——
玩家跳起来不但躲不开，还"够不着"，观感就是**"太高了，跳起来撞不到"**。

**四档正确取值（都验算过语义 + 安全区宽度）：**

| top | 语义 | 安全区 |
|---|---|---|
| `596` | 必须跳 | 下方 138px |
| `566` | 必须跳 | 下方 108px |
| `440` | 不能跳 | 上方 100px |
| `406` | 不能跳 | 上方 134px |

**★ 判据有三条，缺一不可：**

1. **语义正确**：要么"必须跳"，要么"不能跳"
   —— 绝不能"站着跳着都过"（障碍形同虚设），
   也绝不能"站着跳着都撞"（死局）
2. **在可达范围内**：鸟盒要与【恐龙可达的盒区间 `[410, 676]`】相交
   —— 否则玩家跳起来够不着，等于"别跳"的惩罚而非障碍
3. **安全区 >= 60px**：否则是"帧级精度才活得下来"的伪死局

> ⚠️ **这是双向受限的**：太低则跳起来也撞（无解），
> 太高则跳了也够不着（失去意义）。
> **改任何物理参数后都要重新验算全部四档。**

> ★ **踩过的坑（判据写错方向）**：第一版断言拿"鸟盒"去比
> **"恐龙 top 的区间"** `[354,564]`，于是低飞鸟（盒 604..676）被判成
> "够不着"而失败。其实该比的是**"恐龙可达的盒区间"** `[410,676]`
> —— 因为鸟只需与恐龙的**身体盒**相交，不需要与"头顶位置"相交。
> 这两者差一个盒子的高度。

### 3.4 ★★★ 约束二：哪两种障碍不能同时出现

把恐龙能处的每个 `y` 都验一遍，求「对两个障碍都安全」的区间宽度：

| 组合 | 公共安全区 | 判定 |
|---|---|---|
| 大仙人掌 + **低飞鸟** | 91px | ✅ 够宽（为仙人掌跳起来就顺带越过了鸟） |
| **大仙人掌 + 高飞鸟** | **15px** | ❌ **实战不可能打中 -> 等同死局** |
| 低飞鸟 + 高飞鸟 | 71px | ✅ 够宽 |

**结论：大仙人掌与高飞鸟不能同时挡路。**

**解法：一波只出一种障碍**，且间隔满足时间约束：

```
两障碍到达恐龙的间隔 = waveGap / speed
最坏情况（最高速 1500）：1450 x 0.85 / 1500 = 0.82s
跳跃全程 = 2 x 1600 / 6100 = 0.525s
-> 余量 0.3s，来得及落地再跳下一个  ✓
```

> **★ 注意真正的约束不是「两个障碍不能同屏」**（屏宽 1600，
> 而 waveGap ~1000 是会同屏的），
> 而是「**处理完前一个后有时间回到地面**」。

### 3.5 ★★★ 约束三：组宽预算 —— 障碍【太宽】也是死局

"一波只出一种障碍"解决了**种类**冲突，但**宽度**冲突同样致命：

障碍越宽，恐龙要"悬在它上方"的时间越久，而滞空时间是有限的。

```
跳跃全程 = 2 x 1600 / 6100 = 0.525s
恐龙盒底高于「大仙人掌顶(144px)」的窗口 = 0.343s

能越过的最大障碍宽度 = speed x 窗口 - 恐龙盒宽(76)
```

| 速度 | 最大可越宽度 |
|---|---|
| **620（初始）** | **137px（17 格）** |
| 1000 | 267px（33 格） |
| 1500（封顶） | 439px（55 格） |

**★ 为什么这条在 R27 才暴露：** 之前仙人掌是**写死的 5 档**，
最宽的双株组合只有 112px —— 在初始速度的 137px 预算内，"碰巧"安全。

R27 改成**运行时随机拼 1~4 株**（见 §4）后，
最宽可以是 **4 株大仙人掌 = 288px**，是初始预算的 **2 倍多** ——
**第一波就可能必死**，而且不报错。

**解法：株数按【当前速度的组宽预算】递减**（见 `makeCactus`）：

```lua
budget = maxClearWidth(最高株高, 当前速度)   -- 含 20% 安全余量(WIDTH_SAFETY)
n = maxStalks
while n >= 1 do
  grp = randomCactusGroup(n, rnd)
  if grp.w * CELL <= budget then break end   -- 太宽就减一株
  n = n - 1
end
```

**副作用是好的：株数自然随速度增加**（初始 1 株 -> 封顶 4 株），
这正是"难度递增"的几何依据，而不是手感偏好。

> **回归：** `test_dino_rules.lua` 第 4 节穷举所有 120 种 1~4 株组合，
> 并对 `620~1500` 每个速度验证"限宽后 5340 次随机组全部可跳过"；
> 同时【反证危险存在】：不限宽时最宽 288px > 初始预算 109px。

### 3.6 碰撞盒必须按【每一档精灵】单独配

不同精灵的点阵外形不同，用一个通用值会**误判**
（看着没撞却判死，或反过来漏判）：

```lua
-- 翼龙：上下左右都留空（喙只占 2 格宽）
{ name = "bird", w = 20, h = 10, ground = false,
  hitL = 20, hitW = 120, hitT = 8, hitH = 72 },
```

**★ 仙人掌组合的碰撞盒要【按实际点阵逐列量】出来**，不能用控件尺寸：
组合后株与株之间有空隙，用控件尺寸会"看着没撞却判死"。

## 四、仙人掌随机拼株

**需求（用户原话）：** 「仙人掌应该用代码随机组合 1~4 个，不是硬写的」

**旧做法（已推翻）：** 把「单株大/中/小 + 双株小 + 中+小」**写死**成 5 档。

### 4.1 库 API

```lua
sprite.joinStalks(stalks, gap)        -- 底部对齐拼接 -> { rows, w, h }
sprite.randomCactusGroup(count, rnd)  -- 随机挑株型（1~4 株）
sprite.cactusGroup({1,3,2})           -- 确定性组合（测试/按难度指定）
```

### 4.2 ★★ "底部对齐"是这个函数存在的唯一理由

三种单株高度不同（**大 18 / 中 17 / 小 12 格**）。

- 若**顶部对齐** → 矮的那株**脚就悬在半空**，
  真机上看起来"仙人掌浮起来了"，而代码**不会报错**
- 所以按 `(总高 - 自身高)` 行偏移写入

**实测尺寸（宽 x 高，格）：**

| 株数 | 宽度范围 | 高度 |
|---|---|---|
| 1 | 5 / 6 / 9 | 12 / 17 / 18 |
| 2 | 10~18 | 12 / 17 / 18 |
| 3 | 15~27 | 12 / 17 / 18 |
| 4 | 20~36 | 12 / 17 / 18 |

> ⚠️ **株数必须再受 §3.5 的组宽预算约束** ——
> 4 株大仙人掌 = 36 格 = **288px**，初始速度下**必死**。

> ⚠️ **语义陷阱**：`randomCactusGroup(n, rnd)` 里的 `n` 是
> **调用方指定的株数**（它一定返回 n 株），"随机"体现在**每株挑哪种**。
> 真正决定"这一波出几株"的是 demo 的 `makeCactus`（按预算递减）。
> 测试第一版误以为 `n` 是"随机上限"，断言"株数会变"而失败 —— 已修正。

## 五、翼龙四档高度与三帧扇翅

### 5.1 四档高度

数值与判据见 §3.3。四档全部落在跳跃可达区间 `[354, 564]` 内。

### 5.2 ★★ 三帧扇翅

**旧做法（已推翻）：** 只有 2 帧（抬 / 放）来回切换 ——
看起来是**"抖"**，不像扇翅膀。

**新做法：三帧循环**（抬 -> 半收 -> 放 -> 半收 -> 抬）。

| 帧 | 矩形数 |
|---|---|
| 翅抬起（主帧） | 15 |
| 翅半收（新增） | 14 |
| 翅放下（扇翅帧） | 12 |

**★ 两条硬约束：**

1. **三帧点阵尺寸必须严格一致（20x10）** ——
   否则扇翅时会**横向错位**（容器尺寸按 20x10 固定）
2. **障碍槽要按【三帧里矩形最多的那一帧】建节点** ——
   否则某帧多出的矩形**没有控件可画，会缺一块**

**★ 帧表只定义一次**（`sprite.birdFrames()`），demo 与测试都从这里取
—— 避免"两处各抄一份、改了一处忘另一处"。

## 六、难度曲线

**需求（用户原话）：** 「游戏刚开始应该只有单个仙人掌，没有鸟，
往后难度变大再增加鸟和仙人掌的数量和密度」

**实现 = 按【已跑距离】分 4 个阶段**，逐级放开四个量：

| 阶段 | dist 分界 | 最多株数 | 出鸟概率 | 鸟档数 | 波间隔 |
|---|---|---|---|---|---|
| 1 | `< 4600` | **1** | **0.00** | **0** | 1100 |
| 2 | `< 24000` | 2 | 0.25 | 2（只"必须跳"） | 1000 |
| 3 | `< 40000` | 3 | 0.45 | 4 | 950 |
| 4 | `>= 40000` | 4 | 0.60 | 4 | 900 |

**★ 为什么用「距离」而不是「分数」：** 距离是速度的积分，
与"障碍跑得多快"直接对应；分数只是一个换算过的显示值
（`score = dist x 0.012`）。

**★ 阶段2 只开放【必须跳】的两档鸟** ——
先让玩家学会"看到鸟就跳"，阶段3 再引入"有的鸟不能跳"。
**避免一上来就把两种相反的规则同时丢给玩家。**

### 6.1 ★★★ 分界值有【三条】约束，缺一条就会"阶段形同虚设"

#### 约束 A：必须按【速度曲线】标定

速度在 `dist=1665` 到 700、`dist=9628` 到 1000、`dist=29159` 封顶 1500。

**第一版分界写成 `3000 / 7000 / 12000`，结果几乎感觉不到难度变化** ——
`12000` 才进阶段4 时速度已近封顶，等于**前 20 秒一直停在"最简单"档**。

#### 约束 B：必须 >= 第一波的出场距离

```
阶段1 的 waveGap = 1100  ->  第一波在 dist ~1100 才生成
第一版把第一阶段的分界设成 900
900 < 1100  =>  第一波生成时【已经是阶段2】
```

**症状：** 开局第一波就是 **2 株**仙人掌（112px），第 2 波就出鸟 ——
与需求完全相反，而且**不报错**。阶段1 那段配置**从头到尾没被执行过**。

**判据（已写进回归）：**

```
STAGE_DIST[1] > 阶段1 的 waveGap        -- 至少盖住第一波
STAGE_DIST[1] / waveGap >= 3            -- 才算"开局学习期"
```

现在 `STAGE_DIST[1] = 4600`，`4600 / 1100 ≈ 4` 波 ✓

#### 约束 C：过渡期（阶段2）必须够长

阶段2 是**"无鸟 -> 有鸟"的过渡期**，必须长到玩家**确实见到鸟**。

```
曾把阶段2 的分界设成 14000  ->  阶段2 只有 9 波
而 birdChance = 0.25 -> 9 波全不出鸟的概率 = 0.75^9 = 7.5%
★ 实测那一轮就是 0 鸟
```

**后果：** 玩家可能**一只鸟都没见到**就进入阶段3 ——
而阶段3 会出现"**不能跳**"的鸟，规则正好相反。
**等于跳过了教学直接考试。**

**判据（已写进回归）：** 阶段2 的波数 >= 10
（`1 - 0.75^10 = 94.4%` 至少见到一只）。

现在阶段2 的分界是 24000 -> 约 19 波，
见到鸟的概率 `1 - 0.75^19 = 99.6%` ✓

### 6.2 实际节奏（纯逻辑复刻实测）

| 阶段 | 用时 | 分数 | 波数 |
|---|---|---|---|
| 1 | ~6.4s | ~77 | 4 波（纯单株、无鸟） |
| 2 | ~24s | ~350 | 约 19 波属阶段2 |
| 3 | ~35s | ~490 | — |
| 4 | 此后 | — | — |

### 6.3 ★★ 开局有一段空白是有意的

阶段1 的波间隔是 `1100px`，所以**开局约 1.6 秒内屏幕上没有障碍**

> "跑到第一波真的出现（上限 400 帧）"。

## 七、测试方法学

### 7.1 三个套件的分工

| 套件 | 验什么 |
|---|---|
| `test_dino_rules.lua` | **纯数值**：可解性几何、组宽预算、阶段配置（**不跑引擎**） |
| `test_demo_dino.lua` | 物理/碰撞数值（独立复刻状态机）+ 精灵渲染 |
| `test_demo_dino_run.lua` | **端到端**：真在 mock 引擎上跑，验开局/重开/无泄漏 |

### 7.2 ★★★ 交叉校验：测试抄的常量必须与 demo 一致

`test_dino_rules.lua` 头部自己抄了一份 `G` 表（为了能做纯数值验算）。
但那意味着：**若 demo 改了而测试没改，所有断言依然全绿** ——
而真机上跑的是 demo 的那套数值。

**所以第 8 节直接读 demo 源码，逐项比对关键常量**
（`GROUND_Y` / `GRAVITY` / `JUMP_V` / `DINO_HIT_*` / `BIRD_YS` /
`WIDTH_SAFETY` / 翼龙碰撞盒 …）。

> 这是「**测试替身必须忠实**」那条教训的应验
> （见 `引擎能力与限制.md` §七）。

### 7.3 ★★ 验证方法学：mock 里没有"完美玩家"

想验证"阶段4 会不会正常放开"，第一反应是**跑真实 demo 跑久一点**。
但 mock 里没有完美玩家：

```
自带的 AI 每 5~8 波就撞死 -> 分数归零 -> dist 重置
=> 永远到不了 dist 24000+，阶段3/4 根本观测不到
```

**而且这会造成一个更隐蔽的误判：** 用"当前分数 / 0.012"反推 dist 时，
死亡重开后的波会被**算成阶段1** —— 于是统计出
"阶段1 有 94 波、其中还有鸟"，看起来像 bug，实际是**统计口径错了**。

**正确做法：分两层验证。**

| 层 | 手段 | 验什么 |
|---|---|---|
| **生成侧** | 纯逻辑复刻（含精确的 `rnd()` 消耗顺序） | 各阶段实际生成什么 |
| **表现侧** | 真实 demo 跑第一局 | 开局真的只有单株仙人掌 |

> ⚠️ **复刻必须逐行对齐 `rnd()` 的消耗顺序**，否则分布失真。
> 第一版把 `makeCactus` 的重试消耗写成**累加**（`2+1=3` 次），
> 而真实是**只消耗成功那次的 n**（2 次），
> 于是得出"阶段2 出鸟率 0%"的错误结论，白查了一轮。

### 7.4 ★★ 注释里写旧的常量值会破坏"源码级校验"

`test_dino_rules.lua` 用正则从 demo 源码里抓常量：

```lua
src:match("STAGE_DIST%s*=%s*{([^}]*)}")
```

**这个正则用的是 `match`（不是 `gmatch`），只会命中第一处。**
我在注释里写了"第一版写 `STAGE_DIST = {900, 5000, 20000}`"作为历史记录，
结果**正则命中了注释里的旧值**，三条新断言全部误报失败。

> **教训：源码级校验与"注释里复述旧值"是天然冲突的。**
> 要么注释里不写完整字面量（改成 `900 / 5000 / 20000` 这种散写），
> 要么校验改成只认代码行。

## 八、昼夜更替

**需求（用户原话）：** 「添加昼夜更替效果，黑天背景变成深色，天空加上星星和月亮」

**实现 = 两套主题 + 按距离来回切换。**

| | 白天 day | 夜晚 night |
|---|---|---|
| 背景 bg | `#f7f7f7` | `#14161c` |
| 前景 fg（字色 + 地面线） | `#535353` | `#d8dce6` |
| 精灵 sprite | (83, 83, 83) | (216, 220, 230) |
| 提示 hint | `#6a6a6a` | `#8a93a8` |
| 星月 sky | `false`（隐形） | `true`（显形） |

切换节奏：`DAYNIGHT_DIST = 12000`px（约 14 秒）。
`phase = floor(dist / 12000)`，**偶数白天 / 奇数夜晚**；开局是白天。

### 8.1 ★★ 过渡方式：交给引擎 Tween，而不是每帧改颜色

**第一版是"瞬切"** —— 理由是"渐变要每帧改颜色，太浪费"。
但用户反馈**过渡不够丝滑**，所以改成**平滑过渡**（见 §8.9）。

**★ 关键：平滑不是靠"自己每帧改颜色"实现的**，而是
给元素声明 CSS `transition`，由**引擎的 `game.Tween` 负责插值**：

```css
.scene, .ground, .score, .over, .hint {
  transition: background-color 0.8s linear, color 0.8s linear;
}
```

**★ 为什么这样才划算：**

| 做法 | 代价 |
|---|---|
| 自己每帧改颜色 | 每帧 5+ 次写入，且要自己维护插值状态 |
| **交给 `transition`** | **只在切换那一帧创建一次 Tween**，插值由引擎做 |

而且 `bgColor` / `fontColor` / `imageColor` 都是官方文档标注的
**Tweenable** 字段，天然支持插值。

> ⚠️ 注意：这条一开始**完全不生效** —— 撞上了渲染器"脏字段清缓存"
> 与 `isFirst` 判断的冲突（库级 bug）。排查过程见 §8.9。

### 8.2 ★★★ 必须同时改的五个地方（漏一个就露馅）

| # | 改什么 | 漏了的症状 |
|---|---|---|
| ① | `.scene` 背景（bgColor） | 天不变色 |
| ② | 文字色（fontColor） | 深色天上深色字，**看不见** |
| ③ | 文字框**自身背景** | 深色天上三条浅色底条（R21 的延伸） |
| ④ | 地面线（bgColor） | 地面线还是深灰，与浅色前景不搭 |
| ⑤ | 所有精灵矩形（imageColor） | 天变了但恐龙/仙人掌没变，割裂 |

**★ ③ 是最容易漏的** —— 因为 R21 要求文字框必须显式写
`background-color`，所以换主题时这三个框的背景也得跟着换。

**★ ①②④ 走 `bgColor`（textbox 字段），⑤ 走 `imageColor`（image 字段）
—— 两条完全不同的通路，不能指望只改一条。**

### 8.3 ★★★ 星月显隐：两次踩坑才定下来的方案

**需求是「白天没有星月、夜里出现」。这里连着踩了两个坑。**

#### 坑 1：`show/hide` + 缓存控件引用 -> flaky

最直觉的写法是 `sky:show()/hide()`，同时把控件引用缓存起来备用。
实测**同一份代码连跑 6 次，颜色时对时错**。

根因（`webui_render.lua` 的回收段）：

```
节点 display:none
  -> 渲染器把控件【还回控件池】，并标 _orphan = true
  -> 池子是【共享】的，那些控件随时会被别的节点取走
  -> 缓存的引用指向了别人 -> 染色写错对象
  -> 等 show() 时控件又是从池里新取的，带着别人的颜色
```

#### 坑 2：改用 `imageColor` 的 alpha 当隐形 -> 真机无效

为了绕开还池问题，我改成**星月常驻 `display:block`，
白天把 `imageColor` 的 alpha 设成 0**。

**mock 里全绿，但真机白天仍然看得见星月**（用户截图实锤）。

> **★ 为什么判断错了：** 我引用的是 R16 的实测 ——
> 裁剪容器用 `imageColor = Color.FromRGBA(0, 0, 0, 0)` 做到「自身透明」。
>
> 但那是 **`enableMask` 裁剪容器**场景，语义是
> 「遮住遮罩图自身的白边」；与「普通图片控件调透明度」**不是一回事**。
>
> **这是「从一个场景的实测外推到另一个场景」——
> 属于过度推断，正是本项目反复强调要避免的。**

#### ★ 最终方案（两条同时满足才成立）

| # | 做法 | 为什么 |
|---|---|---|
| ① | 显隐用 `sky:show()/hide()` | 语义明确（`display:none` -> 控件 `active=false`），真机可靠 |
| ② | 染色**不缓存控件引用**，每帧用 `rendered.live[node]` 现查 | 躲开还池导致的引用失效 |

```
applyTheme(theme):
  1) sky:show() / sky:hide()      -- 先改 DOM
  2) paintSprites()               -- 立刻染（能覆盖非隐藏的精灵）
  3) 开补染窗口（REASSERT_FRAMES = 6 帧）
```

**★ 为什么需要补染窗口（跨帧）：**
`show()` 只改了 DOM 的 `display`，控件是**下一帧 flush** 才从池里
配给节点的 —— 那一帧之前现查也查不到。实测需要 2 帧才稳定，
留 6 帧余量。

**★ 验证：** 白天全部 sky 控件 `active=false`；
夜里新配的控件 `active=true` 且颜色正确。
`test_demo_dino_daynight.lua` 连跑 5 次稳定 54/54。

#### ★★ 附带的一个陷阱：同名控件会有两份

`show()` 之后，mock 的控件列表里**同一个 name 会同时存在两份**：
还池前的旧控件（`active=false`）与新配的控件（`active=true`）。

> 按 name 找控件时必须**优先取 `active=true` 的那个** ——
> 否则读到的是旧控件，会误判成「没生效」。
> （测试第一版就是这样，白查了一轮。）

**教训推广：** 只要一处 UI 需要「整组隐藏再显示」，就要同时处理
**引用失效**与**同名重复**两件事。

### 8.4 星月点阵（`webui_sprite`）

| 精灵 | 点阵 | 矩形数 | 说明 |
|---|---|---|---|
| 月亮 | 8x8 | 6 | 月牙（右侧挖空） |
| 星星 | 5x5 | 3 | 十字星芒 |
| 小星 | 3x3 | 3 | 远景细碎星 |

**★ 星星为什么是「十字」而不是实心方块：**
8px 格宽下实心方块看起来只是个「点」，缺乏星芒感；
十字（5 格）更像原版。代价是矩形数多 1~2 个，但星星数量少，可接受。

**★ 星月统一用 5px 格宽**（不是默认的 `CELL=8`）：
8px 下大星会变成 42x42 的「大色块」，5px 下才是 25x25 的星芒。

> ⚠️ **月亮也必须显式传 5** —— 漏传会退回默认 8，
> 月亮变 64x64，与星星比例失衡（写这段时刚踩过，
> 表现为测试里「控件尺寸对不上」）。

### 8.5 星星的布局

10 颗星（3 大 + 7 小）位置**写死在 HTML 里**（`SKY_STARS`），
不是运行时随机 —— 星星不参与碰撞，写死可让节点数一次到位，
运行时不新增控件。

**★ 位置刻意避开**分数栏（右上 `1080..1520 x 60..98`）与地面活动区，
免得挡住关键信息。

### 8.6 ★ 性能：切换时才写颜色

`updateDayNight` 先比 `phase`，**变了才调 `applyTheme`** ——
不是每帧写。

单次切换要写 200+ 个控件的 `imageColor`，但：
- 颜色写入很便宜（44.9 微秒/次）
- 切换很稀疏（每 12000px ≈ 14 秒一次）

所以代价可忽略。**反过来（每帧写）才是浪费。**

**回归：** `tests/test_demo_dino_daynight.lua`（53 条断言）。

### 8.7 ★★★ 白色方块：漏染色的矩形会露出方形图原色

**用户反馈：** 「有时会出现错误的白色方块渲染」
（截图里：翼龙背上一个白方块、仙人掌右侧一根白柱）。

**根因：** 方形图 `100001` 是**白→灰渐变**。
控件只要**没被染色**，显示出来就是**白色**。

而 `sprite.apply` 旧实现只在 `wasHidden`（本次从隐藏变显示）
时才调 `reimage` 重贴图+染色：

```lua
-- 旧实现
local wasHidden = n._displayOverride == "none"
n:show()
if wasHidden and type(reimage) == "function" then pcall(reimage, n) end
```

**问题：** 控件池是共享的 —— 一个**一直可见**的节点，
它的控件也可能因为别处的隐藏/显示被换成池里另一个
（那个控件可能没贴图、或 `imageColor` 是默认值）。
旧实现认为"一直可见就不需要重贴"，于是**白块留在屏幕上**。

**修法：** `apply` 对**每一个要显示的矩形**都调 `reimage`。

> 代价：一次换姿态约 32 个矩形 × 2 次 pcall（SetImage + 染色）。
> 而换姿态每几帧才一次，可接受。

**★ 同时修了 `reimageNode` 的引用来源：**
必须**现查 `rendered.live`**，缓存只作兜底且要查 `_orphan` ——
否则会把图/色写到池里别人的控件上（同样是白块的成因）。

### 8.8 ★★ 死在天黑时，重开必须回到白天

**用户反馈：** 「如果死亡在黑天不会从白天重新开始」。

**根因：** `reset()` 只把 `S.dayPhase` / `S.theme` 改成白天，
**没有把主题写进 DOM** —— 真正改颜色的是 `applyTheme`。

而 `updateDayNight` 只在 `phase` **变化**时才调 `applyTheme`：

```
reset 后 dist = 0  ->  phase = 0
S.dayPhase 也被 reset 成 0
=> phase == S.dayPhase  ->  认为"没变化"
=> applyTheme 永远不被调用  ->  背景停在夜晚配色
```

**修法：** 重开分支里**显式应用一次白天主题**：

```lua
if S.over then
  reset()
  ...
  applyTheme(G.THEME.day)   -- ★ 关键：立刻回到白天
  return
end
```

> **★ 教训：** "把状态设对"和"把状态渲染出来"是两件事。
> 任何**依赖"变化检测"来触发渲染**的设计，在"状态被直接重置"
> 时都会漏掉一次渲染 —— 要么显式触发，要么让重置也走正常路径。

**回归：** 第 8 节做了**行为级**验证 ——
真的让角色死在夜晚，再按键重开，断言背景立刻变回白天色。

### 8.9 ★★★ 昼夜过渡做成「丝滑」（修了一个库级 bug）

**用户反馈：** 「白天和黑夜的过度不够丝滑」。

**做法：** 给承载颜色的元素加 CSS `transition`，
库会把它翻译成引擎的 `game.Tween`（`bgColor` / `fontColor` 都是 Tweenable）：

```css
.scene, .ground, .score, .over, .hint {
  transition: background-color 0.8s linear, color 0.8s linear;
}
```

> ⚠️ **刻意不给 `.sky` 加** —— 星月是 image 控件，靠 `display` 显隐，
> `transition` 对它没有意义。

**★ 但一开始它完全不生效** —— 查出来是个**库级 bug**：

```
setStyle("background-color")
  -> 标记 _inlineDirty
  -> 渲染器清 diff 缓存：last.bgColor = nil
  -> setColor 里 prev == nil  =>  isFirst = true
  -> isFirst 为真时不做过渡，直接写值
```

**"改颜色"本身就会清掉 `prev`**，而 `isFirst` 恰好依赖 `prev` ——
于是"改颜色触发的过渡"**永远走不到 Tween 分支**。

**修法（改库）：** 清缓存时对**颜色字段保留 `prev`**
（详见 `引擎能力与限制.md` §4.9）。

**★ 另一个坑：`game.Tween` 是"真机才有的能力"，mock 里没有。**
所以渲染器那段 `type(game.Tween) == "function"` 的代码
**在本地永远不执行** —— 本地全绿，只有真机走 Tween。
已把 `game.Tween` 补进 `engine_mock.lua`，
这样"过渡有没有真的走 Tween"变成**可测**的。

**回归：** 第 10 节断言换主题时 `game.Tween` 被调用、
目标字段含 `bgColor`、时长为 0.8s。

### 8.10 月亮拉长

**用户反馈：** 「再把月亮拉长一点」。

原来的月亮是 **8x8**（接近正方），像是"被咬了一口的烧饼"。
现在改为 **6x12** 的细长弯月（高:宽 = **2:1**），更接近真机的月牙观感。

- 矩形数：6 -> 7（多一个）
- 连通性：单一整块 ✓；重建零误差 ✓
- 尺寸：`6 x 5px = 30px` 宽、`12 x 5px = 60px` 高
