### 逐帧驱动的替代方案

`OnUpdate` 不可用，但**递归 `TweenSequence` 有效**：

```lua
local function tick()
  -- 每帧逻辑
  local seq = game.TweenSequence()
  seq:AppendInterval(1/30)
  seq:AppendCallback(tick)
  seq:Play()
end
```

**R13 实测：698 帧 / 14 秒 / 0 错误。**

## 三、控件类型与能力（11 类客户端控件）

| 控件 | 视觉字段 | 光标事件 | 备注 |
|---|---|---|---|
| **容器节点** | ❌ **无 bgColor/text/fontColor** | ❌ | 只组织子控件；有 `showCursor` 门控 |
| **文本框** | ✅ bgColor / text / fontColor / fontSize | ❌ | 能显示一切，能嵌套 |
| **预设按钮** | ❌ **无视觉字段** | ✅ 完整 8 种 | 外观全靠模板内部结构 |
| 文本视窗 | — | — | 带滚动与裁剪 |
| 图片 | ✅ imageColor（`imageId` 字段只读，但 **`SetImage` 可换图**） | ❌ | 遮罩形状 = 图片 alpha，**任意形状**（见 §4.3） |
| 界面动效 / 全屏动效 | — | — | |
| 按键提示 | — | — | |
| **光标检测区域** | — | ✅ | 与预设按钮能力相近，无 `interactable` |
| 网格视窗 | — | ❌ | 原生滚动+裁剪 |
| 模板引用控件 | — | — | |

### 3.1 关键限制：字段按类型封死

```
容器节点写 bgColor  → 失败（字段不存在）
容器节点写 text     → 失败
预设按钮写 bgColor  → 失败
预设按钮写 text     → 失败
```

**写入不支持的字段会静默失败**（`pcall` 返回 false），不报错。

### 3.2 关键限制：**自定义字段一律不可写**

> ★ 这是最隐蔽、代价最大的限制。

```lua
c.__myField = 123          -- 静默失败
print(c.__myField)         -- nil
```

**探针证据（`probe_field.lua`）：**

```
自定义字段:  __webuiParent  写=false  读=true  值=nil
             myCustomFlag   写=false  读=true  值=nil
引擎字段:    bgColor        写=true   读=true  值=...
             text           写=true   读=true  值=...
父子 API:    GetChildren()  ✅ 返回正确子列表
```

**含义：控件上无法保存任何自定义状态。** 需要状态时只能：
- 存在**外部 Lua 表**里（用控件做 key）
- 或改用**引擎自身 API** 查询（如 `GetChildren`）

### 3.3 无 reparent API

控件创建时挂到父下，**之后无法改变父**。

**推论：** 控件池复用时，**必须复用父匹配的控件** —— 否则它会被引擎按旧父渲染，坐标完全错乱。

## 四、渲染能力边界

> **本节只回答「引擎能做什么 / 做不到什么」。**
> 「用这些能力做某个游戏时，数值/几何/难度该怎么定」属于**设计约束**，
> 见 [小恐龙游戏实现.md](小恐龙游戏实现.md)。

### 4.1 能力速查表

| 想要的效果 | 能否实现 | 方式 |
|---|---|---|
| 纯色块 | ✅ | 文本框 `bgColor` |
| 文字 + 字号 + 颜色 | ✅ | 文本框 |
| **矩形裁剪 `overflow:hidden`** | ✅ **可实现** | **图片控件 + 矩形图当遮罩 + `enableMask`**（R17 实证，见 §4.4） |
| **任意形状裁剪** | ✅ | 遮罩形状 = 图片 alpha，**等比适配不变形**（见 §4.3、§4.4） |
| **几何图形（圆/方/三角/星/箭头）** | ✅ | **图片控件 + `SetImage` 换图**（首选，无缝）／字符（退路，有缝） |
| **无缝长条 / 进度条 / 底衬** | ✅ | **文本框 `bgColor` 纯色块**（实测 478px 区间数=1，零断裂，见 §4.2） |
| **运行时换图** | ✅ | **`SetImage(imageSource, imageId)`**（R16 实测生效，见 §4.3） |
| 圆角 / 边框 / 阴影 | ❌ | 只能预配图片（6 个字段写入全部失败，见 §4.3） |
| 粗体 / 斜体 | ❌ | 文本框无 `font-weight` |
| 富文本 | ❌ | 一个文本框一种样式 |
| 自定义字体 | ❌ | 无加载 API |
| 缩放 / 旋转 | ✅ | `localScaleX/Y`、`localRotationZ` |
| 渐变动画 | ✅ | `game.Tween` |

`fontSize` **必须是整数**（真机报错）。

### 4.2 几何图形：文本框 + Unicode 字符（R15 真机验证，2026-10-07）

**结论：几何图形不必用图片，用文本框打几何字符即可，且可染色；
但字符【不能无缝拼接】，按「是否无缝」分工使用。**

> 状态：字符可用性 + 字体度量 + 无缝方案均为**真机实测**
> （`probe.lua` 模块 `glyph` + 截图逐像素测量）。

#### 可用字符集（真机截图确认渲染正常）

| 用途 | 字符 |
|---|---|
| 状态点 / 图例 | `●` `○` |
| 方形标记 / 复选框 | `■` `□` |
| 菱形 / 装饰 | `◆` `◇` |
| 三角（四向，实心空心） | `▲` `△` `▼` `▽` |
| 评级 / 收藏 | `★` `☆` |
| 勾选 / 关闭 | `✓` `✕` |
| 方向指示 | `→` `←` `↑` `↓` |
| 框线 | `│` `─` `┌` `┐` `└` `┘` `├` `┤` `┬` `┴` `┼` |

**这些字符全部渲染正常，无豆腐块。** 对比图片方案的优势：

- 不用配模板、不占 `image` 控件池
- `fontColor` 染色（CSS `color`），**可 Tweenable** → 颜色渐变动画
- 资源零成本

```html
<span class="dot"></span>
```
```css
.dot { color: #fff; font-size: 16px; }
.dot.warn { color: #ffcc44; }
```

#### ★ 真机实测度量（R15 探针，2026-10-07）

**探针：`probe.lua` 模块 `glyph`（真机跑通），截图逐像素测量。**

两组独立实测，**advance 比例恒定**：

| 采样 | 字号 | 字形宽 | 缝 | advance | advance / 字号 |
|---|---|---|---|---|---|
| 第 1 组 | 32 | 41px | 10px | 51px | **1.594** |
| 第 2 组 | 16 | 19px | 6px | 25px | **1.562** |

**引擎字体是比例字体，`■` 的占位恒为 ≈1.56~1.59em，不是 1em。**
连排固定留缝（`@32` 为 10px），**拼不出无缝长条**。

**推论：缝随字号等比缩放 → `localScale` 拉伸只会等比放大，压不掉。**

单个 `■` 的 bbox = **41×40px**（宽高比 1.025）→ **单图形是正方形**，
可作为**离散**图形用，但不能当"可平铺的格子"。

#### ★★ 无缝方案：纯色块 `bgColor`（两处独立实证）

**要无缝，就别走字符 —— 用文本框 `bgColor` 纯色块。**

| 方案 | 实测（截图像素） | 区间数 | 判定 |
|---|---|---|---|
| **A. 白色纯色块** | `y=174..209`，`x=561..1038`，宽 **478px** | **1** | ✅ **零断裂** |
| **D. 深色底条 + `●` 字符** | `y=261..321`，`x=1521..1997`，宽 **477px** | **1** | ✅ **零断裂** |

**D 尤其重要** —— 它是「**无缝底衬 + 字符点缀**」的组合方案：
底条（`bgColor`）完全无缝，`●`（`fontColor`）正常叠加其上。**这是推荐做法。**

> **Δ 换算常数：截图像素 = 画布单位 × 1.6**（2560 屏 / 1600 画布）。
> 验证：声明宽 300 → 实测 478px，`478/300 = 1.593` ✓

#### 字体度量实测（参考值）

| 字体来源 | `■` advance / em |
|---|---|
| 微软雅黑（本机，比例字体） | 0.454 |
| 黑体 / 宋体（本机，全角） | 0.990 |
| **引擎内置字体（真机测）** | **1.59** |

**三组数据两两不同，方向还相反** —— 所以**字体度量必须真机实测，
不能用系统字体推算**（已并入 §七 方法学）。

#### 结论：按「是否无缝」分工

| 需求 | 方案 | 无缝？ |
|---|---|---|
| 长条 / 进度条 / 底衬 / 边框 | **文本框 `bgColor` 纯色块** | ✅ **实证无缝**（478px 区间数=1） |
| 底衬 + 字符点缀组合 | **`bgColor` 底条 + 字符 `fontColor`** | ✅ 底条无缝，字符叠加其上 |
| 状态点 / 星级 / 勾选 / 箭头 / 三角 | **字符 + `fontColor` 染色** | ❌ 有缝，但本就该离散 |
| 圆形 / 圆角 / 头像框 | 图片控件 + `enableMask` | ✅ 图片本身连续 |

**字符的价值在「非矩形小图形」，不在「拼长条」。**
需要无缝的地方用纯色块更省、更准。

#### 其他真机确证

| 结论 | 证据 |
|---|---|
| **`fontSize` 必须整数** | 设 `16.5` → `写=false`；设 `31.7` → `写=false` 且保持旧值 |
| **`game.Tween` 是 3 参数** | 传 4 个报 `(3 expected, got 4)`；正确：`Tween(obj, {field=val}, 时长)` |
| **`SetActive(true)` 必需** | 新控件 `active` 默认 `false`，不激活则完全不可见 |
| **画布尺寸是浮点** | `1599.9998 × 899.9998`，**不要用 `== 1600` 判断** |
| 字符写入通路 | 30 个字符全部可写入、可读回、渲染正常，**无豆腐块** |
| `fontColor` 染色 | ✅ 可用，且**可 Tween**（颜色渐变） |
| `bgColor` 纯色块 | ✅ 无缝，478px 单区间（不经字体排版） |

#### ⚠️ 边界

1. **字符画不等于矢量图形。** 大幅缩放会暴露字形边缘的锯齿。
2. **缝随字号等比变化，比例恒定 1.56~1.59em。** 拉伸压不掉。
3. **`fontSize` 必须整数**（引擎限制）。
4. **控件挂载位置受 `Root` 可视范围限制。** R15 实测：8 条 2×4 网格中
   仅 3 条出现在画面内，**声明坐标在画布范围内也可能不显示** —— 布局要多轮验证。

**探针：`probe.lua`（模块 `glyph`），本地试跑：`test_probe.lua`。**

### 4.3 图片控件：遮罩、换图、裁剪（R16 真机验证，2026-10-07）

**探针：`probe.lua` 模块 `mask`（真机跑通），截图逐像素分析。**

#### 4.3.1 ★★ 遮罩形状 = 图片的 alpha，**不是固定圆形**

真机实测：遮罩形状**完全由图片资源本身决定**。同一组子控件（400×400 红色文本框）
塞进 160×160 图片控件，切换图片后遮罩形状随之改变：

| 当时加载的图 | mask 状态 | 红色子块的实际形状 | 红色像素占比 |
|---|---|---|---|
| 圆形 `100002` | 开启 | **圆缺角**（Pac-Man 形） | 15.4% |
| 三角形 `100003` | 开启 | 被裁出**三角形斜边** | 19.3% |
| 四角星 `100004` | 开启 | 被裁出**凹形缺口** | 29.5% |
| —— | **关闭** | **完整矩形（实心）** | **64.4%** |

**结论：**
- `enableMask = true` → **按图片 alpha 裁剪子控件**
- `reverseMaskArea` → 反转保留区域
- **能裁子控件**（旧文档存疑的 Q2，答案是**能**）
- **形状任意** —— 圆、三角、星、环，**取决于你用哪张图**

**实用含义：** 想要什么裁剪形状，就配一张什么形状的图。`▓` 头像框、技能环、
雷达底图全部可行，而且**子控件内容会被正确裁切**。

#### 4.3.2 ★★ `SetImage` 运行时换图**可用**

字段 `imageId` / `imageSource` 确实**只读**，但存在**专门的 Setter 方法**：

```lua
-- ✅ 正确
img:SetImage(Enum.ImageSource.StaticReference, 100002)

-- ❌ 字段赋值（只读，无效）
img.imageId = 100002
```

**真机实测结果：**

```
顺序A (imageSource, imageId): 调用=true  读回imageId=100002 ← 变了!
顺序B (imageId, imageSource): 调用=false err: ImageSource expected, got integer

调用成功 6/6，确认改变 5/6
  圆形 100002 / 三角形 100003 / 四角星 100004 / 五角星 100005 / 圆环 100006
  → 全部 ✓ 确认改变
```

**签名确认为 `SetImage(imageSource, imageId)`** —— 与 `client_control_api.md` 第 814 行一致。

> ⚠️ **一个图片控件就能动态显示任意形状/图标**，无需为每个形状建模板。

#### 4.3.3 真实枚举结构

**⚠️ 枚举名不能照 `client_control_api.md` 猜** —— 该文档第 586 行写的是
`Enum.ImageSourceImageStaticReference`，而真机实际是 `Enum.ImageSource.StaticReference`
（**没有重复的 `ImageSource` 前缀**）。

实测的真实结构：

```
Enum.ImageSource            (8): Currency, Equipment, Faction, Item,
                                 Prefab, Skill, StaticReference, UnitStatus
Enum.ImageType              (2): Basic, Stretch
Enum.ImageFillType          (6): Horizontal, Radial180, Radial360,
                                 Radial90, Unused, Vertical
Enum.ImageFillRadialType    (4): Bottom, Left, Right, Top
Enum.ImageMaskSoftEdgeMode  (2): Percentage, Pixel
```

**正确用法：**

```lua
img:SetImage(Enum.ImageSource.StaticReference, 100002)
img:SetFillRadial360(Enum.ImageFillRadialType.Bottom, 0.75)
```

**⚠️ `Enum` 顶层遍历得到 0 项**（`pairs(Enum)` 为空），但 `Enum.ImageSource`
等可**直接索引取到** —— 说明 `Enum` 用了**元表**，`pairs` 看不到成员。
**枚举名必须显式取，不能靠遍历发现。**

#### 4.3.4 圆角 / 边框：**确证不可行**

六个候选字段**写入全部失败**（`写=false`，读回 `nil`）：

```
borderRadius / cornerRadius / radius
borderWidth / borderColor / enableBorder
```

**`border-radius`、`border` 无法实现**，只能靠预配圆角图或遮罩。

> 注：本地 mock 试跑时这六个字段显示 `写=true`（因为 mock 不校验字段），
> **真机 `写=false` 才是硬证据** —— 再次印证「测试替身必须忠实」。

#### 4.3.6 ★★★ 矩形裁剪：**可实现**（R17 实证，2026-10-07）

用**矩形图**（`100001`）当遮罩 + `enableMask=true`，**子控件被正确裁成矩形**。

**实验设计：** 父（裁剪窗口）`200×100`，子块 `400×200`（故意溢出 2 倍）。

| 阶段 | 遮罩图 | 子块实测（截图像素） | 形状特征 | 判定 |
|---|---|---|---|---|
| **矩形图 + mask** | `100001` | **285×143** | 中线 287 / 1/4 处 **287**（等宽） | ★ **矩形裁剪成功** |
| 圆图 + mask | `100002` | ~287×143 | 中线 287 / 1/4 处 **249** | ★ **正圆** |
| 三角图 + mask | `100003` | ~283×141 | 中线 143 / 1/4 处 **74** | ★ **三角形** |

**关键尺寸对比**（截图像素 = 画布 × 1.6）：

```
若【未裁剪】→ 子块应显示 ~640×320 px（完整 400×200）
若【被裁剪】→ 应限制在 ~320×160 px（父的 200×100）
实测 285×143  →  落在【被裁剪】区间 ✓
```

**结论：**
- ✅ **`overflow:hidden` 可实现** —— 滚动列表、卡片裁切、文本溢出**全部解禁**
- ✅ **遮罩形状随图片变化且正确**（矩形/正圆/三角分别验证）
- ✅ **等比适配，不拉伸变形** —— 圆形图在 2:1 的父里仍是**正圆**：
  实测 1/4 高度处宽/中线宽 = `249/287 = 0.868`，理论正圆值 `0.866` ✓

> **意义：这是本项目最大的一次能力解禁。**

**探针：`probe.lua`（模块 `mask`）。**

### 4.4 文字渲染的硬约束：框高 / 字号 ≥ 1.8（★★ R19 实证）

**这是本项目最隐蔽的一条限制 —— 症状是"文字凭空消失"，而所有数据都正常。**

引擎的文本框有**字号自适应**（`adaptiveFontSize` / `minimumFontSize`，见
`client_control_api.md` 第 839-840 行）。**框不够高时，它把字压到极小或干脆不画。**

#### 实测分界线

| 字号 | 框高 | **框高/字号** | 结果 |
|---|---|---|---|
| 14px | 26 | **1.86** | ✅ 显示 |
| 15px | 28 | **1.87** | ✅ 显示 |
| 15px | 22 | 1.47 | ❌ 不显示 |
| 17px | 28 | 1.65 | ❌ 不显示 |
| 20px | 42 | **2.10** | ✅ 显示 |
| 26px | 36 | 1.00 | ❌ 不显示 |
| 30px | 42 | 1.40 | ❌ 不显示 |

**阈值 ≈ 1.8。**

**两组交叉验证（只改一个变量）：**

| 组 | 只变什么 | 结果 | 说明 |
|---|---|---|---|
| 1 | 同 15px，变框高 | 28高 ✅ / 22高 ❌ | **框高决定** |
| 2 | 同 42高，变字号 | 20px ✅ / 30px ❌ | **比值决定，非字号绝对值** |

> **第 2 组关键**：`20px` 能显示，**推翻"字号有上限"的猜测** ——
> 决定因素是**比值**，不是字号本身。

#### 实践规则

```css
/* ❌ 框太矮 -> 字被自适应压掉 */
.t { font-size: 15px; height: 22px; }

/* ✅ 框高 ≥ 字号 × 1.9（留余量） */
.t { font-size: 15px; height: 29px; }
```

**调字号时务必同步调框高与框宽**（框宽不足会让文字被截断）。

### 4.4.1 ★★ 文本框【必须显式指定背景色】（R21 实证，2026-10-08）

**这是与 §4.4 同级的隐蔽陷阱 —— 症状是"文字看不清"，而布局全对。**

**实测（真机截图逐像素量得，探针截图分析）：**

```
底条颜色   (49,48,48)   亮度 48
文字颜色   (46,45,45)   亮度 45
                  对比度差 = 3      ← 几乎完全看不见
```

**根因：** CSS 里**不写 `background-color`** 时，引擎给文本框画的是
**默认深色底**（实测 `#535353`，即 `(83,83,83)` 量到的近 `(49,48,48)`）。
若字色也是深色（如 `color: #535353`），**字与底同色 → 文字消失**。

> ⚠️ 这与"白底页面"的直觉相反：页面亮着，不代表文本框也是透明的。
> **文本框有自己的底色，默认是深色。**

**正确做法 —— 每个带文字的框都显式写背景：**

```css
/* ❌ 依赖引擎默认底 -> 深底深字，看不见 */
.msg { width:800px; height:80px; color:#535353; font-size:40px; }

/* ✅ 显式指定背景，与页面底色一致 = 视觉上"透明" */
.msg {
  width:800px; height:80px;
  color:#535353; font-size:40px;
  background-color:#f7f7f7;   /* ★ 必须 */
}
```

**回归测试：** `tests/test_demo_dino_style.lua` 断言**所有有文字的
文本框 `bgColor` 都不能为 `nil`**，并验算字/底对比度 > 100。

### 4.4.2 ★★ 需要居中就必须写 `text-align`（R21 实证，2026-10-08）

**症状：文字全部贴在框的左边，看起来"没居中"。**

**实测：** 一个 `width:800px` 的框，文字占 328px：

```
文字左边距   3.8px
文字右边距 473.8px      ← 差 470px
```

**根因：** `text-align` 默认值是 `left`（见 `webui_style.lua` 默认样式表）。
不写就永远是左对齐 —— **框居中 ≠ 文字居中**。

```css
/* ❌ 只有框的位置居中，文字仍贴左边 */
.msg { left:400px; width:800px; }

/* ✅ */
.msg { left:400px; width:800px; text-align:center; }
```

`text-align` 已映射到引擎的 `horizontalAlignment`
（`center` → `Enum.TextHorizontalAlignmentMiddle`，`right` → `Right`）。

> **推论：** `left` + `width` 决定的是**框**的位置；
> 文字在框内怎么摆是**另一件事**。定位正确不代表观感正确 ——
> 真机截图测量才能同时验证这两层。

### 4.4.3 ★★ 承载文字的子控件必须继承背景色（R21 修复）

**症状：** 裁剪容器（`overflow:hidden`）里的卡片背景色"不对"。

**根因：** 裁剪容器是 **image 类型**，自身没有 `text` 字段，
库会额外挂一个 **textbox 子控件**承载文字（§4.3.6）。
这个子控件是**新建的控件** → 吃到**引擎默认深色底**，
而不是父元素 CSS 声明的 `background-color`。

```
声明: .cbox { background-color:#204020; color:#fff; }
修复前: 文字子控件 bgColor = (83,83,83)   ← 引擎默认深色底
修复后: 文字子控件 bgColor = (32,64,32)   ← = #204020 ✓
```

**修复**（`webui_render.lua`）：渲染文字子控件时继承父的 `_bgColor`：

```lua
if st2._bgColor then
  tsetColor("bgColor", st2._bgColor)
end
```

**父没有背景色时什么也不做** —— 这很关键：
`overflow:hidden` 容器**本来就不该**设背景（§4.5.2），
此时不能误刷成不透明。

**回归测试：** `tests/test_clip.lua` 第 9 节（撤销修复即失败）。

### 4.4.4 ★★ 引擎默认底色是**深色**，不是透明（R21 核心结论）

**这是 §4.4.1 和 §4.4.3 的共同根因，单独列出。**

**实测（真机截图逐像素）：**

```
底条颜色   (49,48,48)   亮度 48     ← 未写 background-color 时的实际底色
文字颜色   (46,45,45)   亮度 45
                  对比度差 = 3      ← 几乎完全看不见
```

**文本框的默认底色是深色 `#535353`，不是透明。**

这意味着两条实践规则：

| 场景 | 正确做法 |
|---|---|
| 页面上放文字 | **显式写 `background-color`**（想"透明"就写页面同色） |
| 裁剪容器里的文字 | 父**不要**设背景，由**子层**承载底色；文字子控件继承它 |
| 页面底是亮色时 | 别以为文本框也是亮的 —— 它是深的 |

**已注入 `tools/engine_mock.lua`**：新建 textbox 时 `bgColor` 默认
`#535353`，这样本地就能测出"忘了写背景 / 忘了继承背景"两类 bug。

> ⚠️ 不能再用 `bgColor == nil` 判断"没写背景" —— 它**永远不为 nil**。
> 正确的判据是**对比度**（字色与底色的亮度差 > 100）。

**探针：** 见 `docs/探针模块归档.md`（`text` 模块重建要点）。

### 4.5 四个真机 bug（连续两轮定位，2026-10-07）

**这四个都是库的实现缺陷，症状各具误导性。已全部修复并加回归测试。**

| # | Bug | 症状 | 根因 |
|---|---|---|---|
| 1 | `flex-direction:column` 忽略子项 `width` | 圆形被拉成**扁椭圆**；裁剪容器变宽导致色带不再溢出 | 布局器无条件把子项宽度设为父容器宽度 |
| 2 | `intrinsicWidth` 重复计算 `margin` | 容器比内容宽出一个 margin → **白竖条** | `intrinsicWidth` 含 margin，调用方又加一次 |
| 3 | 裁剪容器填充不受自身遮罩约束 | 圆外跑出**暗色月牙** | `enableMask` 只裁子控件，控件自身填充不受约束 |
| 4 | **遮罩图自身可见** | 裁剪边缘一圈**白边** | `SetImage` 后图会显示，而形状图是白色渐变 |

#### 4.5.1 布局相关的两个（#1 #2）

**#1 症状链条**（一处 bug 引发三个现象）：

```
flex column 忽略 width
  -> .avatar 实际 980x130（声明 130x130）
  -> border-radius:50% 按 980:130 适配 -> 扁椭圆
  -> .relic 实际宽 980（声明 260）
  -> 400 宽的色带够不到边界 -> 裁剪看不出效果
```

#### 4.5.2 裁剪相关的两个（#3 #4）

**裁剪容器的正确配置（库已自动处理）：**

```lua
-- 库在渲染时自动做这三件事：
ctrl:SetImage(Enum.ImageSource.StaticReference, 形状图)  -- ① 设遮罩形状
ctrl.enableMask = true                                   -- ② 开启裁剪
ctrl.imageColor = Color.FromRGBA(0, 0, 0, 0)             -- ③ ★ 自身透明
```

**③ 是关键** —— `SetImage` 后**控件会显示这张图**，而形状图是白→灰渐变，
不置透明就会在裁剪边缘露出一圈白边。

**三组对照实测（只差 `imageColor`）：**

| 组 | imageColor | 白边 | 圆形 |
|---|---|---|---|
| A | 不设 | ❌ 白色月牙 | 圆 |
| **B** | **全透明** | ✅ **干净** | **圆** |
| C | 红色 | 边缘变红 | **形状不变** |

**C 组证明**：`imageColor` **只影响遮罩图的显示颜色，不影响遮罩形状**。

**⚠️ 另外：不要给裁剪容器设 `background-color`。**
它的填充不受自身遮罩约束，会溢出到裁剪区之外（见 #3）。
需要底色时，**在容器内放子元素承载**：

```html
<div class="card">              <!-- 裁剪容器，无背景色 -->
  <div class="card-bg">         <!-- 铺满并承载底色 -->
    <div class="band"></div>    <!-- 溢出的内容，会被裁掉 -->
    <div class="text">生之花</div>
  </div>
</div>
```

**⚠️ 底色层不能是与父等高的"兄弟层"** —— 那会把后续兄弟挤出父容器而被裁掉。
**底色必须画在"包住所有内容"的那一层上。**

**探针：`probe.lua`（模块 `text` / `clip` / `mask` / `glyph`）。**

**问题：** 裁剪必须用**图片控件**，但图片控件**没有 `text` / `bgColor` 字段**
（实测写入 `text` 读回 `nil`）—— 那么 `overflow:hidden` 的容器里怎么放文字？

**实测结论：能装。** **对照页（`probe.lua`）全部正常显示文字**：

| 组 | 结构 | 结果 |
|---|---|---|
| B | textbox 父 + 直接文字 | ✅ |
| K | **image 父 + 直接文字** | ✅ |
| L | image 父（无底色）+ 直接文字 | ✅ |
| M | textbox 父 + 有底色 | ✅ |
| N1 | **image 父 + 直接文字** | ✅ |
| N2 | **image 父 + 子元素文字** | ✅ |
| N3 | textbox 父 + 子元素文字 | ✅ |
| C | **image 父 + 子元素文字** | ✅ |
| F | **裁剪父 + 子元素文字** | ✅ |
| P | 裁剪父 + 子元素 + 子元素有底色 | ✅ |
| Q | 裁剪父 + 子元素（底色=白） | ✅ |

**两种结构都能用：**

```html
<!-- ① 文字直接放在裁剪容器里 -->
<div class="card" style="overflow:hidden">卡片文字</div>

<!-- ② 文字放在子元素里（推荐，可独立设样式） -->
<div class="card" style="overflow:hidden">
  <div class="title">生之花</div>
  <div class="sub">沉沦之心 +20</div>
</div>
```

**库的处理（`render.lua`）：** 当裁剪元素**自带直接文字**时，
自动额外挂一个 `textbox` 子控件承载文字（父 `image` 负责裁剪，子 `textbox` 负责显示）。

> ⚠️ **重要教训：字段「没有」不等于「装不了内容」。**
> 图片控件确实没有 `text` 字段，但它的**子控件**可以有 ——
> 容器能力与自身字段能力是两回事，下结论前要区分。
> 此前认为必须绕开的 `overflow:hidden`，实际可用一个图片控件当裁剪容器实现。

```lua
-- 之后塞进 clip 的子控件，超出部分会被裁掉
```

### 4.6 ★★ 逐帧性能成本模型（R22 真机实测，2026-10-08）

**问题：** 用多个图片控件拼出复杂图形（如恐龙），每帧更新坐标，
真机扛得住吗？—— 决定了"能不能做像素级图形"。

#### 4.6.1 成本模型（拟合误差 < 0.21ms）

```
每帧耗时(ms) = 11.92 + 0.0449 × 写入次数
```

| 档位 | 控件数 | 写入/帧 | 纯工作 ms |
|---|---|---|---|
| L1 现状 demo | 10 | 20 | **13.03** |
| L2 拼一只恐龙 | 40 | 80 | **15.32** |
| L3 恐龙+障碍 | 80 | 160 | **19.01** |
| L4 最坏情况 | 160 | 320 | **26.38** |

**两条关键推论：**

| 项 | 数值 | 含义 |
|---|---|---|
| **单次写入** | **44.9 微秒** | 写入**极便宜** —— 34 个矩形全量更新仅 ≈ **1.5ms** |
| **固定开销** | **11.92 ms/帧** | 与 DOM 节点数正相关，**与写入次数无关** |

> ★ **优化方向是「减节点」，不是「少写字段」。**
> 固定开销占 30fps 预算（33.3ms）的 **36%** ——
> 即使一个字段都不写，每帧也要花 11.9ms。

#### 4.6.2 ★★ 计时方法学：必须把「等待」和「干活」分开

**第一轮探针量出 4 档全是 38~45ms，与负载无关** —— 看似"写入很慢"，
实则是**探针缺陷**：

```
循环里 AppendInterval(1/30) = 33.3 ms 是【每帧的等待】
os.clock 量的是【真实经过时间】-> 量到的主要是"等下一帧"
```

**验证：** 负载放大 16 倍，耗时只差 7.8%（42.2 → 45.5ms）。
若耗时真由写入决定，L4 应约 675ms。

**正确做法 —— 只累计工作耗时：**

```lua
local t0 = os.clock()
-- ... 写入 + flush ...
workTime = workTime + (os.clock() - t0)   -- ★ 不含任何等待
```

> **教训：** 性能探针里，`os.clock` 的差值只有在
> **紧贴被测代码**时才有意义。夹着 `AppendInterval` 的循环
> 量到的是**调度间隔**，不是性能。

#### 4.6.3 真机调度抖动（同轮实测）

| 项 | 值 |
|---|---|
| 探针设定间隔 | 33.3 ms（1/30） |
| 实测含等待 | 38.2 ~ 45.4 ms |
| **抖动** | **约 5 ~ 12 ms** |

**真机的 `TweenSequence` 调度本身就有 5~12ms 抖动** ——
做手感敏感的游戏时，**不要假设帧间隔精确**，
物理应该用**固定步长**（本项目 `onTick(dt)` 就是这么设计的）。

**探针：`probe.lua`（模块 `perf`）。**

### 4.7 ★★ 多矩形拼像素图形：引擎侧的四条硬约束（R22/R23/R24）

**背景：** 引擎**不能导入外部图像**，预置资源只有 6 张形状图。
想画不规则图形，只能把点阵**分解成矩形**，每个控件画 1 个矩形。

**★ 结论：这条路是通的**（2026-10-08 真机确认），
但必须同时满足下面 **4 个条件** —— 缺一个就失败，且**症状各不相同**：

| # | 条件 | 违反的症状 |
|---|---|---|
| 1 | 矩形写 `position:absolute` | 全堆成一列（一根竖条） |
| 2 | 相邻矩形外扩 1px（bleed） | 形状上有缝 |
| 3 | **用 image 控件，不用 textbox** | **块变圆、形状碎掉** |
| 4 | asImage 模式不写 `background-color` | 被选回 textbox -> 回到第 3 条 |

> **排查顺序建议：先看"是不是圆的"，再看"有没有缝"。**
> 圆角会同时制造"变圆"和"缝"两个症状，先解决它更省事。

**★ 性能：** 写入极便宜（44.9 微秒/次），真正的成本是
**固定 11.92ms/帧**（与节点数正相关）——
所以优化方向是**减节点**，不是"少写字段"。见 §4.6。

**工具：** `lib/webui/webui_sprite.lua`（点阵 -> 贪心矩形分解 -> HTML）。

> **⚠️ 具体游戏的数值与设计**（点阵尺寸、摆放几何、可解性、难度曲线）
> 属于**设计约束**而非引擎能力，见
> [`小恐龙游戏实现.md`](小恐龙游戏实现.md)。
#### 4.7.1 ★★ 坑 1/2：布局与缝（R23 真机截图定位）

**这两条都只有真机能发现，mock 测试全绿也照样出问题。**

**坑 1：矩形必须 `position:absolute`，否则全堆成一列**

```
症状：33 个矩形全挤在父容器左边，纵向依次排开
      -> 屏幕上一根竖条，不是图形
      实测宽度 47px（应为 176px）

根因：inline 的 left/top 对【静态流布局】元素无效
```

> **教训：库不该依赖调用方记得配 CSS。**
> `toHTML` 现在把 `position:absolute` 写成**内联样式**。

**坑 2：相邻矩形之间露缝（更隐蔽）**

```
症状：形状铺开了，但上面有一条条缝 —— 相邻块之间露出背景色
      实测缝宽 1.25 ~ 4.38px，缝里是纯背景色 (255,251,243)

根因：真机上色块的实际渲染宽度【比声明值略小】
      而点阵内部有几十条相邻边界 -> 每条都是一条缝
      （实测：某 22x24 点阵有 45 条）
```

**解法：每个矩形四边各向外扩 1px（bleed）。**

```lua
left = (r.x-1)*cell - bleed
top  = (r.y-1)*cell - bleed
w    = r.w*cell + bleed*2
h    = r.h*cell + bleed*2
```

**验证：外扩 1px 后，点阵的每个填充格全覆盖、每条内部边界无缝**
（用几何覆盖模型逐格验算，回归见 	est_sprite.lua 第 10 节）。

代价是轮廓胖 1px —— 但同色压在同色背景上，看不出来。

> ⚠️ `toHTML`（初始生成）与 `sprite.apply`（换姿态）**必须用同一个
> bleed 值**，否则姿态切换后缝又回来。

#### 4.7.2 ★★★ 坑 3：文本框模板【自带圆角】（R24）

**真机确认（2026-10-08）：纯色块（textbox）默认就是圆角的，小块直接变圆。**

**实测数据（截图逐像素量得）：**

```
声明 8x8 的色块 -> 真机画成 15x15 的【圆】
逐行宽度: 2, 7, 11, 11, 13, 13, 15, 15, 15, 13, 13, 12, 11, 9, 4
          （矩形每行该是 15 —— 这是标准圆形轮廓）
```

**圆角半径 ≥ 8px**（因为 8px 的块被完全圆化成圆）。

**影响范围（实测统计）：**

| 尺寸 | 数量 | 是否变形 |
|---|---|---|
| 8×8 | 12 | ✅ 变圆 |
| 8×16 / 16×8 | 4 | ✅  |
| 24×8 / 32×8 / 40×8 / 56×8 | 4 | ✅  |
| 8×40 / 8×56 / 16×40 | 3 | ✅  |
| 32×24 / 32×104 / 48×48 / 48×56 | 5 | ❌ 只是圆角矩形 |

> **★ 某 33 个矩形的样本里 29 个（88%）至少一个维度 ≤ 16px -> 全部变形。**
> 而像素画里【大量细长条正是 1 格宽】—— 形状会被彻底毁掉。

**这也解释了"缝"的真正来源：**

圆角把每个矩形的**四角切掉**，相邻矩形的角对不上 → 露背景。
**外扩（bleed）只能补"宽度差"，补不了"角被切掉"。**

> **一个根因，两个症状：圆角既让形状变圆，又制造了缝。**

**为什么代码改不了：**

`borderRadius` / `cornerRadius` / `radius` 等 6 个字段
**真机写入全部失败**（§4.3.4）。圆角来自**控件模板的外观**，
是编辑器里的设置，不是字段。

**可选解法（★ 已选定方案 1）：**

| 方案 | 做法 | 状态 |
|---|---|---|
| **① 改用 image 控件** | `data-image="1"` + `SetImage(方形图)` | ✅ **已采用** —— image 模板是方的（编辑器确认） |
| 加大 bleed | 外扩 3~4px 盖住四角 | 形状会明显发胖变浑 |
| 改用大色块 | 避开小尺寸（都不 < 2R） | 只能做抽象轮廓 |
| 改模板 | 编辑器里去掉模板的圆角元素 | 需模板本身可编辑 |

**① 的实施（R24）：**

```lua
sprite.toHTML(rects, { asImage = true })   -- 生成 data-image 控件
-- 渲染后调一次：
sprite.setImages(clip, dom, doc, prefix, count, 100001, ui.rendered)
```

**两个要点：**

1. **asImage 模式不能写 `background-color`** ——
   写了会被 `chooseKind` 规则② 选成 **textbox**，圆角又回来了。
2. **换姿态时，从隐藏变显示的矩形要重贴图** ——
   控件可能已被控件池回收，图会丢。
   `sprite.apply(..., reimage)` 提供这个钩子。

**实测结果：** 换上 image 控件后，全部矩形都是 `image` 类型、
0 个误用 textbox，换姿态后仍保持。

> ✅ **2026-10-08 真机确认：用多控件拼像素图形这条路是通的**，
> 但必须满足本节开头列的**全部 4 个条件**。

**模块：** `lib/webui/webui_sprite.lua`。
**回归：** `tests/test_sprite.lua` 第 8~10 节。

### 4.8 ★★★ 隐藏节点会被【移出 rendered.live】，控件引用随之失效（R28）

**这是一条渲染器行为，不是引擎 API —— 但它会让代码「静默写错对象」。**

#### 4.8.1 行为

```
节点 display:none
  -> 渲染器把它的控件【还回控件池】，并标 control._orphan = true
  -> 同时 self.live[node] = nil（该节点不再有 live 条目）

节点 display 恢复
  -> 重新 chooseKind + 从池里【取一个控件】配给它
  -> 取到的可能是【别的节点刚还回来的那个】
```

**关键点：控件池是【共享】的。**一个控件今天属于 A 节点，
A 隐藏后可能被 B 节点取走。

#### 4.8.2 症状：不报错，只是画错

```lua
-- 缓存了控件引用（比如建控件时存下来的）
local ctrl = myCached[node]
ctrl.imageColor = someColor     -- ★ 可能写到了【别人的】控件上
```

- **不会报错**（字段写入本来就成功，只是写错了对象）
- 表现为**颜色/样式时对时错**（flaky）——
  取决于池子里恰好剩哪个控件

> **实测（R28）：** 用 `show()/hide()` 切换星月显隐后，
> 同一份代码连跑 6 次，颜色结果不一致。改为常驻显示后 5/5 稳定。

#### 4.8.3 ★★★ 正确做法

| 场景 | 做法 |
|---|---|
| 需要"整组隐藏/显示" | 用 `display`（`show()/hide()`）—— 语义明确、真机可靠 |
| 隐藏后再操作该节点 | **不要缓存控件引用**；每帧用 `rendered.live[node]` 现查 |
| 必须缓存引用 | 只在【节点可见且稳定】时用（如换姿态重贴图） |

**★ 关键组合：`show/hide` + 现查引用，两条必须同时满足。**

- 只用 `show/hide` 但缓存引用 -> **flaky**（引用被池里别人取走）
- 想靠 `imageColor` 的 alpha=0 隐形 -> **真机无效**（见下）

> **⚠️ 不要用 `imageColor` 的 alpha 当"隐形"手段。**
>
> R16 实测的是**裁剪容器（`enableMask`）**场景 ——
> 那里 `imageColor = (0,0,0,0)` 的作用是"遮住遮罩图自身的白边"。
> 把它外推到"普通图片控件调透明度"是**过度推断**：
> 实测真机上白天星月**仍然可见**。
>
> **教训：一个场景的实测不能直接外推到另一个场景** ——
> 即使 API 签名看起来一样（都是 `imageColor`）。

#### 4.8.4 ★★ 附带陷阱：同名控件会同时存在两份

节点隐藏再显示后，控件列表里**同一个 `name` 会有两条**：

```
div#sky   active=false    <- 还池前的旧控件（name 没被清掉）
div#sky   active=true     <- 渲染器新配的（正在用的）
```

> **判据：正在用的那份是 `active == true` 的。**
> 按 name 查控件时若不区分，会读到旧控件 -> 误判成"没生效"。

> **★ 通用判据：** 只要代码里出现"**跨帧保存控件引用**"，
> 就要问一句"这个节点会不会被 display:none"。
> 会的话，引用就不可靠。

**实例：** `deploy/demo_dino.lua` 的昼夜更替（星月层）。
**设计侧说明：** [`小恐龙游戏实现.md`](小恐龙游戏实现.md) §8.3。

### 4.9 ★★★ CSS transition 与「字段脏标记」的冲突（R28 修）

**症状：给元素写了 `transition`，运行时改颜色却【直接跳变】，过渡不生效。**

#### 4.9.1 原因链

```
脚本 setStyle("background-color", ...)
  -> 标记 node._inlineDirty["background-color"]
  -> 渲染器清 diff 缓存：clearField("bgColor")
  -> last.bgColor = nil
  -> setColor 里 prev == nil  =>  isFirst = true
  -> isFirst 为真时【不做过渡】，直接写值
```

**关键：** "改颜色"这件事本身就会把 `prev` 清掉，
而 `isFirst` 的判断恰恰依赖 `prev` —— 于是
**"改颜色触发的过渡"永远走不到 Tween 分支**。

#### 4.9.2 修法

清缓存时对**颜色字段保留 `prev`**：

```lua
-- 颜色字段：保留 prev（它本来就是"上一次写入的值"）
local KEEP_PREV = { bgColor = true, fontColor = true, imageColor = true }
local function clearField(f)
  if KEEP_PREV[f] then return end
  if last[f] ~= nil then last[f] = nil end
end
```

> **★ 为什么安全：** `setColor` 自己会按分量比较决定要不要写，
> 保留 `prev` 不影响正确性，反而让过渡有了插值起点。
>
> ⚠️ **只对颜色这么做** —— 尺寸/位置等字段没有过渡需求，照旧清。

#### 4.9.3 ★★ 验证要点

`game.Tween` 是**真机才有的能力**。早期 `engine_mock.lua` 没有它，
于是渲染器那段 `type(game.Tween) == "function"` 的代码
**在本地永远不执行** —— 本地全绿，真机才走 Tween 路径。

> **已补进 mock**（`E.tweenCount()` / `E.lastTween()` 可观测），
> 这样"过渡到底有没有走 Tween"变成可测的。
> 这是「**测试替身必须忠实**」的又一次应验。

**回归：** `tests/test_demo_dino_daynight.lua` 第 10 节。

### 4.10 ★★★ 一帧之内：`onTick` 先于 `flush`，所以「生成控件」当帧不可见（R29）

#### 4.10.1 行为

引擎每帧被本库驱动成两步，**顺序固定**（`webui.lua` 的 `startLoop`）：

```
① onTick(dt)   —— 游戏逻辑（改 DOM 的状态 / 显隐 / 样式）
② flush()      —— 渲染：布局 + 建控件 + 写字段
```

**推论（本节的要点）：** 在 `onTick` 里对某个节点做的一切，
**本帧的渲染器都还看不到** —— 尤其是：

> **节点刚从 `display:none` 变成可见时，它（及其整棵子树）
> 的控件是在【本帧 flush】才被创建/取用的。**
> 在 `onTick` 里拿 `rendered.live[node]` **必然拿到 nil**。

```
onTick:  node:show()  +  想给它的控件写字段
                          └─ rendered.live[node] == nil  ← 控件还不存在
flush:   渲染器才 _take(kind, parent) 建出控件
         └─ 控件是【模板默认外观】，没有任何人给它写过字段
```

⚠️ **不报错**。`if ctrl then ... end` 静默跳过，只是画面上不对。

#### 4.10.2 症状：新出现的元素「第一帧是错的」

以拼像素图（`image` 控件 + 方形图）为例，方形图是**白→灰渐变**，
所以没被 `SetImage` + 染色的控件**就是一块白**：

```
第 85 帧（生成那一帧）  imageId = nil        ← 白块
第 86 帧                imageId = 100001     ← 补上后正常
```

**★ 危害取决于"之后还会不会有人碰它"：**

| 场景 | 后果 |
|---|---|
| 该元素之后**再不改外观** | 错误**永久保留**（一起留到出屏） |
| 该元素之后**周期性换外观** | 下一轮就"自己好了"，表现为闪烁 |

这正是「固定间隔出现白块 + 同屏一个白一个正常」的成因：
同一波里仙人掌不再换姿态（常驻白块），旁边的翼龙每隔几帧扇翅（自己好了）。

#### 4.10.3 ★★★ 正确做法

**不要依赖"我改它的时候顺手设置一次"** —— 那一刻控件可能还不存在。

改为**每帧对「当前应该可见」的元素补一次外观**，
放在 `onTick` 的**最开头**（正好覆盖上一帧 flush 建出来的控件）：

```lua
local function tick(dt)
  reassertSprites()          -- ★ 每帧补：贴图 + 染色
  ...
end
```

**⚠️ 两个必须注意的点：**

1. **放在早退判断之前**。若这一行写在 `if not started then return end`
   之后，那么"未开始"状态下本来就该可见的元素（如主角）
   永远补不到 —— 开局第一帧就是错的。

2. **不能在节点上缓存"上次设过的值"来跳过重复写。**
   缓存挂在**节点**上，而节点的**控件**会被共享池换掉
   （见 §4.8）；换主之后缓存就开始撒谎 -> 跳过写入 -> 错误外观留下。
   写入很便宜（44.9 微秒/次，见 §4.6），**不值得为此牺牲正确性**。

> **★ 通用启示：** 凡是"创建时机"与"设置时机"可能错开的东西，
> 都不要只设置一次。**幂等的每帧兜底**比"精确的一次性设置"更可靠 ——
> 因为前者错了会自愈，后者错了会静默地一直错下去。

**回归：** `tests/test_sprite_reassert.lua`（19 条断言）。
真机取证探针：`deploy/probe_white.lua`。

#### 5.2.1 ★★ 同一个事件会被【每个绑定它的控件】各收一遍

**R20 实测（探针把同一按键同时挂到 3 个控件上）：**

```
★[捕获] jumpDown   control(textbox) 第1次
★[捕获] jumpDown   control(textbox) 第2次
★[捕获] jumpDown   root(根控件) 第3次
```

**含义：按一次键，3 个监听器各收到一次。** 这不是"触发了 3 次按键"，
而是**同一个事件广播给了所有注册者**。

> ⚠️ **实践铁律：一个按键只能绑一个挂载点。**
> 若把跳跃键同时绑在 root 和某个子控件上，**游戏里按一次会跳 3 次**。
> 实现时**只绑 `root`**（最稳，不随 DOM 重建而失效）。

#### 5.2.2 ★ 按键回调**绝不能 `return true`**

`client_control_api.md` 第 1317 行：

> 按键事件被 Lua 回调标记已处理后，**同容器内其他按键不再响应本次事件**。

**含义：** 回调返回 `true` 会把同容器内其他按键一起吞掉。
探针的 `key` 模块一律 `return false`，且 `tests/test_probe.lua`
有一条**断言**专门守这个回归（故意改成 `true` 会让测试失败）。

#### 5.2.3 待补：按键回调的 `data` 结构

R20 实测 `data.type` **读回为空**（`CursorEventData` 那套
`GetUIPos` / `GetPressUIPos` 取值方式**不适用于按键回调**）。

**当前够用** —— 靠"绑定的是哪个枚举"即可确定是哪个键，
不需要从 `data` 里取键码。若将来需要按键的附加信息，
需再跑一轮探针专门读 `data` 的字段。

**探针：`probe.lua`（模块 `key`）。**

### 6.3 ★★ 根控件（Root）的缩放要设成 **1.01**，否则界面四周有缝

**症状**：页面能正常渲染，但**四周留一圈缝**——本应铺满屏幕的
`.stage`（1600×900）只填了一部分，看起来"没有铺满"。

**实测数据**（对真机截图逐像素量得，缩放比 1.6）：

| 量到的量 | 值（画布单位） |
|---|---|
| 可见内容区 | 1230 × 612 —— **正好是 `.panel` 的尺寸**（不是 `.stage` 的 1600×900） |
| 左缝 / 右缝 | 185 / 184（相等 → 水平居中正常） |
| 上缝 / 下缝 | **7 / 280**（严重不等 → 内容整体挤在顶部） |

**水平完全正确**（`.panel` 应在 `(1600-1232)/2 = 184`，实测 185），
说明布局引擎的居中计算没问题；问题出在**根控件本身的渲染区域**。

**解决**：在编辑器里选中根控件（客户端控件容器），在「变换」面板里设成

| 字段 | 值 |
|---|---|
| 位置 | `X 800` / `Y 450`（画布中心） |
| 大小 | `W 1600` / `H 900`（画布尺寸） |
| **缩放比例** | **`X 1.01` / `Y 1.01`** |

**缩放从 `1.00` 调大到 `1.01` 即可** —— 让控件略微超出画布，四周的缝就被盖住了。

![根控件变换面板：位置 (800,450)、大小 1600×900、缩放 1.01](img/root_scale.png)

> 上图为编辑器里该控件的「变换」面板。**注意缩放是 `1.01`，不是 `1.00`。**

**注意**：这是**编辑器里的手工设置**，库无法代劳
（库只能改 `sizeDelta`，改不了 `localScale`）。
新工程第一次接入 `webui` 时，顺手检查这一项，能省一轮真机排查。

> **排查提示**：这个缝隙**很容易误判成布局 bug**。
> 分辨方法：量「可见内容区的尺寸」——
> 若它等于某个内层元素的尺寸（如 `.panel`）而非最外层（`.stage`），
> 说明布局是对的，问题在**根控件的渲染区域**，不在 CSS。

### 7.1 不要用 `type() == "table"` 守门（附：一次被实测推翻的假设）

> **⚠️ 实测更正（2026-10-07）**：本节早期版本断言"真机上 `game` 是
> userdata，所以 `type(game)=="table"` 短路"——**这个说法被真机实测推翻了**。
> probe 诊断模块读回的事实是：
>
> ```
> type(game)   = table
> typeof(game) = table
> type(script) = table      （但 typeof(script) = Script）
> type(Enum)   = table
> type(Color)  = table
> ```
>
> 所以 **`type(game)` 那个判断并不是 `main.lua` 空白的成因**。
> 真正成因是 §7.2（`OnUpdate` 不被驱动 + 模块 `_ENV` 身份）。
> 下面保留"不要用 type() 守门"这条**通用建议**，但把它与本次 bug 解耦。

**通用建议（与上面的 bug 无关，独立成立）**：判断"能不能调用某 API"时，
只判断**成员是否存在**，不要判断对象本身的类型：

```lua
-- ✗ 脆弱：依赖对象的类型名，换个实现/版本就可能变
if type(game) == "table" and type(game.FindClientUIRoot) == "function" then

-- ✓ 稳健：只关心"这个方法能不能调"
if type(game) ~= "nil" and type(game.FindClientUIRoot) == "function" then
```

**理由**：

- 官方 API 文档说明 `typeof()` 的用途就是**识别宿主对象**；
  `script` 实测 `typeof` 为 `Script` 而 `type` 为 `table` ——
  两者不一致，说明**用 `type()` 判断这类全局对象不可靠**
- 真正决定"能否调用"的是**成员存在性**，不是对象类型
- 本库曾按此原则统一改写 5 处 `type(x) == "table"` 守卫
  （`game` / `script` / `Enum` / `Color`），虽非本次 bug 主因，但方向正确

**教训（关于排查方法本身）**：

> 我曾经**没有任何真机证据**就断定 `type(game)` 是 userdata，
> 并据此改了一版代码 —— 结果用户回"还是没有"。
> **对真机行为的假设，必须先用探针读回来再动手。**
> 这次是靠 `deploy/probe.lua` 的 `mount` 诊断模块（读 `typeof`/`type`/
> `FindClientUIRoot`/prefabs/bound）才拿到事实的。

```lua
if type(game) ~= "nil" and type(game.FindClientUIRoot) == "function" then
  root = game.FindClientUIRoot(app.rootName)
end
```

**改写范围**（本库统一改掉 5 处 `type(x) == "table"` 守卫）：

| 文件 | 原写法 | 现写法 |
|---|---|---|
| `webui.lua` `mount` | `type(game) == "table"` | `type(game) ~= "nil"` + 判方法 |
| `webui.lua` `setUpdate` | `type(script) == "table"` | `type(script) ~= "nil"` + 判方法 |
| `webui_clip.lua` `imageSource` | `type(Enum) ~= "table"` | `type(Enum) == "nil"` 才退出 |
| `webui_clip.lua` `asClip` | `type(Color) == "table"` | `type(Color) ~= "nil"` + 判方法 |
| `webui_clip.lua` `tint` | `type(Color) ~= "table"` | `type(Color) == "nil"` 才退出 |

> ⚠️ 注意：**这 5 处改写都不是 `main.lua` 空白的成因**（成因见 §7.2）。
> 它们是"方向正确的加固"，但当时被错误地当成了主因。

### 7.2 ★★★ 等 Root 不能用 `OnUpdate`（真机"界面空白+无日志"的真正根因）

**症状**：`main.lua`（用 `webui.mount`）界面一片空白、日志里**只有 probe 的** `[PROBE]` 输出，没有任何 `[我的页面]`；而 `probe.lua` 一切正常。

**根因**：两个真机事实叠加。

**事实 ①：`OnUpdate` 在真机上不被驱动**（本文档 §一，R9/R11 实测 `tick=-1`）。

**事实 ②：模块里的 `script` 是模块自己的身份**
（[webui_feasibility.md](webui_feasibility.md)：每个模块独立 `_ENV`，`script` 是模块自己的身份）。

于是 `mount` 里这段**必然失效**：

```lua
-- 库模块（webui.lua）里：
local function setUpdate(on)
  script:EnableUpdate(on)     -- ← 打开的是【模块自己】的逐帧更新
end
```

引擎只调用**入口脚本 `main.lua`** 的 `OnUpdate` —— 而它从未被打开，
`App:update(dt)` 永远不会执行。

**失败链**（真机常态：Root 比脚本晚一帧就绪）：

```
mount() 结束 → _tryMount() 失败（Root 还没建）
             → start() 调 setUpdate(true)   ← 打开了错误的 script
             → 等 OnUpdate 重试                ← 永不触发
             → 永远挂不上，且什么都不打印
```

**为什么 probe 能跑**：它在**入口脚本自己的环境**里调
`script:EnableUpdate(true)`（probe.lua 第 878 行）—— 那才真的驱动了自己的 `OnUpdate`。
**"库模块里调 script" 和 "入口脚本里调 script" 不是一回事**，这是最容易搞混的一点。

**正确做法**：用**递归 `TweenSequence`** 自己驱动重试（R13 实测 698 帧 0 错误）。

```lua
local function tick()
  if app:_tryMount() then ... return end
  -- 续期
  local seq = game.TweenSequence()
  seq:AppendInterval(1/50)
  seq:AppendCallback(tick)
  seq:Play()
end
```

这条路径**不依赖任何 `_ENV` 身份**，与 `ui:startLoop` 是同一套机制。

**同时要改 `mount` 末尾**：Root 未就绪时要顺手启动重试链，
否则只能等调用方调 `start()` —— 一旦时序不对就又静默失败。

**回归测试**：`tests/test_mount.lua` 第 7 节，**故意一次都不调用 `app:update()`**，
只让 Tween 链跑。用旧行为跑该测试会失败（`bound` 恒为 `false`）。

**教训**：

- **`script` 是有身份（_ENV）的** —— 在库里拿到它 ≠ 拿到入口脚本的那个
- **任何"等下一帧"的逻辑都不能建立在 `OnUpdate` 上**
- **"日志里没有我的输出" ≠ "我的代码没被执行"**：`main.lua` 顶层
  本来就不打印任何东西（所有 `print` 都在函数体内），
  加载期静默是正常的 —— 不能据此判断它有没有被加载

## 八、部署机制：真机读 `.gil` 而非文件夹（★ 重要）

**这是本项目最容易浪费真机轮次的坑，单独成节。**

### 8.1 机制

```
关卡目录/
  ├── 1073741828.gil          ← ★ 真机实际读取的脚本内容在这
  └── external_lua_file/
        ├── webui.lua         ← 把文件放这里【不够】
        └── ...
```

- `.gil` 是**关卡文件**，由**编辑器导入**外部脚本时写入
- **`Copy-Item` / 文件复制不会更新 `.gil`**
- 新增文件（如 `webui_clip.lua`）尤其容易漏 —— 编辑器可能不会自动纳入

### 8.2 症状

```
真机报错：  failed to load script 'webui_clip'
本地验证：  ✓ 全部通过（因为验证器读的是文件夹）
```

**「本地全对 + 真机找不到文件」= 同步问题，不是代码问题。**

### 8.3 检查方法

`verify_external.lua` 已内置检查，会打印：

```
========== 关卡文件同步检查 ==========
  关卡文件: 1073741828.gil
  ⚠️ 这是真机【实际读取】的内容，不是文件夹

    clip         已在 .gil 中
    render       已在 .gil 中
    ...
  ✓ 全部模块已同步到关卡文件
```

**原理：每个模块取一个「独有标记」，检查它是否出现在 `.gil` 里。**

```
util → "function U.trim"     clip  → "C.SHAPES"
dom  → "function D.newElement"  style → "_clipShape"
...
```

缺哪个模块会明确列出，并提示「请在编辑器里重新导入」。

### 8.4 操作建议

| 情况 | 做法 |
|---|---|
| 改动**已存在**的模块 | 编辑器通常会同步 |
| **新增**文件 | **需要在编辑器里导入一次** |
| 跑真机前 | **先跑 `verify_external.lua` 确认同步** |

> 这条已写入 `PROJECT.md` 的部署流程。
